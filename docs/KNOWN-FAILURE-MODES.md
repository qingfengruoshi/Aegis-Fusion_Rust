# 已知故障模式（重写规避清单）

**用途**：用户指示「log 方面可以看前面的 bug 报错来规避更多的 bug」。本文把 shell 线 **v1.0.1（正式版）**沉淀下来的故障模式抽成清单，作为重写时的**规避依据**。每条都注明机制——因为「症状单一、病因多元」正是这个项目拖了四天的根本原因。
**来源**：`IntegrityFusion/docs/one-green-postmortem.md`（8 条根因）、`CHANGELOG.md`（73 个小节）、`docs/security-audit-OPEN-ITEMS.md`、以及 13 个脚本注释里的 `field report` / `audit *` 标注。

## 0. 最重要的一条：一绿问题有 **8 个独立病因**，且症状完全相同

> 引用复盘原文：「任意一条命中，Google 服务端给出的都是同一个答案：BASIC。**症状单一、病因多元**，这正是问题拖了四天的根本原因——每修掉一个，下一个才会露出它的症状。」

**对重写的含义**：新实现必须能**分别观测**这 8 条路径的状态，否则一旦复现，你还是只能看到"一绿"。这正是 WebUI 那 95 个探针键存在的理由 —— 它们不是装饰，是**分诊工具**。

## 1. 八个根因（逐条：机制 → 重写必须保留什么）

### 1.1 profile 设备 ID 字段全空 → `CANNOT_ATTEST_IDS`（v2.2.8）

- **机制**：上游 TA 在应用请求带 ID 字段的证明密钥时，拿 profile 预置的 `brand/device/model/serial/imei` 与请求比对；默认配置**全空** → `attestation ID mismatch for brand` → GMS 拿不到 ID 证明 → 仅 BASIC。
- **重写必须保留**：安装期用**本机真实属性**回填 config（IMEI 走厂商属性 → `iphonesubinfo` 兜底）。见 `CONTRACT-management.md` §6（`customize.sh`）。

### 1.2 换箱不生效：TA 不监听文件变化（v2.2.9）

- **机制**：keybox 字节嵌在 daemon **推送帧**里，keystore2 侧 TA 构建一次后**常驻复用**。只换磁盘上的 `keybox.xml`，TA 仍用旧箱作答；旧箱失效时请求**静默转发真机 TEE**（BL 解锁的真硬件证明 = 一绿）。
- **重写必须保留**：`bounce_tees()` 的等价物 —— kill daemon → 重注入 → 重启 keystore2 → 回收 DroidGuard → force-stop Play Store。换箱与强制刷新两条路径都要触发。
- **注**：这条与「daemon 的 FileObserver 收到 MOVED_TO 就重推」是**两个层次**：观察者负责"重推"，bounce 负责"让 keystore2 侧重新构建"。

### 1.3 GMS 不在 TEE 作用域内（v3.0.1，**"一绿元凶"**）

- **机制**：DroidGuard 跑在 `com.google.android.gms` 进程里。GMS 不在作用域 → DroidGuard 拿到**真机**证明 → verdict 恒 BASIC，**keybox 再干净也没用**。
- **重写必须保留**：`apps-sync.sh` 开机**自动播种 GMS 入作用域**（`.gms-scope-seeded` 防重复；**用户移除后不回加**）。
- **为什么容易漏**：IB 自动纳入 GMS，融合模块靠用户手勾 —— 这正是「IB 三绿、融合模块一绿」的第一层差异。

### 1.4 指纹轮换失败 = 指纹清零（v3.0.4，09-08 实机事故）

- **机制**：旧轮换逻辑在生成新指纹**之前**就删旧指纹。轮换触发后 wget 被墙 → 设备从「有一个能用的指纹」变成「一个都没有」→ 之后换什么 keybox 都只有 BASIC。
- **重写必须保留**：**生成成功才替换**；且判定条件是 `rc == 0 **且文件非空**` ——
  > **文件存在 ≠ 生成成功。** 这条区分必须写进实现。

### 1.5 PIFork 配置路径硬编码 → 指纹半从未生效（v3.1.1，Round 12 集成缺陷）

- **机制**：PlayIntegrityFork v18 的 Zygisk 载荷把配置路径**硬编码**为 `/data/adb/modules/playintegrityfix/`（五处文件）。融合版模块 id 不同，该目录从不存在 → `pif-fetch` 写下的指纹**没有任何人读取**，DroidGuard 始终面对真实设备。PI 恒 BASIC，与 TEE 半边状态完全无关。
- **⇒ 这就是 `assemble.sh` 里那段定长二进制路径改写存在的原因**（把 35 字节的 `/data/adb/modules/playintegrityfix/` 替换成本模块 id + 补位斜杠）。
- **重写必须保留**：那五处路径改写的**等价物**，以及它的构建期校验（`grep -qa "$PIF_PATH_NEW"`）。
- **新基座的额外风险**：我们改过模块 id（`aegisfusion_rs`），补位斜杠数随之变化（6 → 3）。`assemble.sh` 现已**程序化计算**并断言长度相等。

### 1.6 身份同步是毒（v3.0.12 → v3.0.13 → v3.0.14，**三次反转**）

这是四天里最曲折的一段：

| 版本 | 动作 | 依据 |
|---|---|---|
| v3.0.12（先立） | 把 `patchLevel.vendor`/`boot` 与 system 一并同步 | Box-Brain 实锤：自称 Pixel 的身份报出小米的 vendor 补丁日期（attestation 202602 vs DroidGuard 202608） |
| v3.0.13（后翻） | **撤回五项身份字段同步**，只保留补丁级同步 | 读 AOSP `system/keymint` 源码定案 |
| v3.0.14（迁移残留） | 修 `ro.product.product` → `ro.product.name` | brand 门禁错误变成 product 门禁错误 |

**v3.0.13 那条源码级别的洞察（必须理解，否则会重犯）**：

> ① TA 的 ID 门禁把 **keystore2 请求来的真机 ID**（keystore2 是原生进程，Zygisk 对它不可见）与 profile 配置比对；
> ② 门禁通过后，**证书编码的是请求里的真机 ID，profile 值从不出现在证书里**。
> ⇒ **同步 Pixel 身份从来不可能让 attestation 变 Pixel，唯一效果就是弄挂整个硬件证明请求。**

### 1.7 keybox「结构合法 ≠ 引擎能用」（v3.1.2 → v3.1.3）

三个子问题，都是**显示与现实脱节**：

- **symlink 毒源（v3.1.2）**：`keybox.xml` 被换成指向 `/data/adb/tricky_store/keybox.xml` 的**符号链接**。持久日志显示分界点前后 daemon 从 `applied=1 failed=0` 变成 `applied=0 failed=1` → `g_profiles` 恒空 → 每个请求 `target=0` 全部转发真机 HAL → 恒一绿。
  > **`[ -f link ]` 会跟随链接，一切存在性检查都被它骗过。** 安装脚本现会把 symlink **实体化**为真实副本。
- **base64 坏体（v3.1.3）**：某 `<Certificate>` 的 base64 体内 `=` 之后还跟着数据（两段 blob 被追加进同一 element）。引擎原话 `61(ASCII '=') 1887(offset)` —— 引擎在**解码阶段**就丢弃整个 keybox。而 v3.1.3 的校验**只查字符集和长度 %4，拦不住**。Rule 5 现按引擎真实实现（`attest.rs:128-138`）做同一件事。
- **渠道三绿是「渠道自述」**：绿格来自渠道服务端对**它自己最新 box** 的报告，与设备本机解析无关 —— 「模块显示三绿、设备实际一绿」的显示缺口由此而来。补上的是**本机吊销检测 + 引擎侧校验**。

### 1.8 检测类应用的 `-66`：从「移出避开」到「引擎层修掉」（v3.1.6 → v3.1.8）

- **机制**：keystore2 用**真机身份**填 `ATTESTATION_ID_*` 标签；TA 里 profile 跟随 PIF 伪装身份；AOSP 参考 TA 逐一比对，不一致即 `CANNOT_ATTEST_IDS`（-66）。**所以 profile 伪装 ≠ 真机时，密钥认证类应用勾进保护列表必然 -66。**
- **v3.1.6**：先解决「静默移出用户勾选」（明示 + `.keep-detectors` 开关 + 诊断导出披露）。
- **v3.1.7**：用户拍板「**解决而不是绕开**」→ **引擎补丁 0005**：由我们的 TA 服务请求时，把请求里的 `ATTESTATION_ID_*` **改写为 profile 值**（门过了，叶子证明伪装身份）；profile 没有的 ID **丢弃标签而非失败**；走真机 HAL 的路径不改写。**排除机制整个退役。**
- **⚠️ 生效条件**：0005 是引擎补丁，**必须重构 TEESim payload（CI `zipTask`）才生效**。本地 zip 内嵌的是既有 `build/teesim-payload.zip` 旧二进制 —— 在 CI 产物刷入前勾选密钥认证仍会 -66，那是旧二进制，不是脚本没生效。

## 4. 复盘的 6 条方法论（对重写同样适用）

1. **复合故障要用开关分解，不要靠直觉逐个猜** —— `.pif-off` / `.pif-sync-off` / `bootkey.bin` 三个杠杆把七层病因拆成了单变量实验；
2. **「已知能过」的参照系是最强的诊断工具** —— Box-Brain 日志与 AS 运行时 config 两次直接推翻当时的"终案"；
3. **读上游源码优先于读日志猜** —— `CannotAttestIds` 的几何关系是从 AOSP 源码读出来的；**日志只能告诉你"门挂了"，源码才能告诉你"这门永远过不去"**；
4. **持久化日志是复合故障的生命线** —— symlink 分界点与 `applied=0 failed=1` 的转变都是跨重启逐行比对定位的；
5. **显示层要如实报告引擎侧状态** —— 渠道绿格、结构校验通过、状态灯全绿都可能是"自述"，与本机实际判定可以完全脱节；
6. **修复不能以「替用户做决定」为捷径** —— v3.1.6 的静默排除是错的方向，v3.1.7 用引擎补丁真正修掉才是终态。

## 6. 环境与实现层陷阱（跨脚本，重写时最容易「修掉」的坑）

这些不是业务逻辑，而是**踩着具体运行时差异形成的写法**。重写时若"顺手清理"，会重新引入。

| # | 陷阱 | 真相 | 出处 |
|---|---|---|---|
| 6.1 | `$((10#09))` 或 `$(( 09 ))` 解析**八进制** | `10#` 是 **bash/ksh 专有**，在 **dash 下是语法错误**；`09` 是非法八进制。**CI 的 `/bin/sh` 是 dash，Git Bash 的是 bash** ⇒ 典型「本地过、CI 挂」。现象：到期感知的 deadline 静默回退成 14 天。**手写去前导零循环**是为了绕开它 | `pif-fetch.sh:66-76` |
| 6.2 | `env VAR=...` 命令前缀 | 在 **Git Bash / MSYS 上见过静默 no-op** ⇒ 代理变量没设上，还得不到任何错误。改用 **`export`** | `pif-fetch.sh:306-309`、`:387-389` |
| 6.3 | busybox `wget --spider` | **busybox wget 不支持 `--spider`** ⇒ 用它做代理探测会让探测**永远失败**、救援路径**不可达**。改用**完整 GET**（`-O /dev/null`） | `pif-fetch.sh:395-398`（audit N9） |
| 6.4 | 继承来的 `http_proxy` | root shell 可能从调用环境（桌面调试、某些管理器上下文）继承代理。**条件式清理只在配置了代理时才 unset** ⇒ 继承的代理会**静默把"直接"这一轮变成走代理**，破坏降级阶梯的判别力，日志里的 `proxy=none` 也变成谎话。必须**无条件 unset** | `pif-fetch.sh:324-337`（audit N10） |
| 6.5 | `[ -f <symlink> ]` | **会跟随符号链接** ⇒ 一切存在性检查都被骗过（keybox.xml 变成指向别处的 symlink，检查全过、引擎全挂）。必须显式**实体化** | 见 §1.7 |
| 6.6 | 「文件存在」当「生成成功」 | 一旦不再预先删旧文件（见 §1.4），磁盘上的文件可能只是**旧幸存者**。成功判定必须是 **`rc == 0` 且文件非空**，否则会错误重启轮换时钟、让陈旧身份续命 | `pif-fetch.sh:355-366` |
| 6.7 | 用 `date` 做日期运算 | 设备上的 `date` applet（toybox / busybox / GNU）**解析格式各不相同** ⇒ 自己用纯整数算（Fliegel–Van Flandern JDN）。"这绝不能成为轮换时钟坏掉的原因" | `pif-fetch.sh:55-83` |
| 6.8 | 静默失败 | **Audit M5 / fail-loud**：包可能没有 seed（构建期抓取失败时 `assemble.sh` 只警告不失败），以前与"任何空状态"无法区分 ⇒ 用户看到"没指纹/PI BASIC"而日志零原因。现在**显式命名原因** | `pif-fetch.sh:183-192` |

> **共同主题**：这个项目的很多"看起来多余的写法"，都是在**具体设备/具体 shell/具体 busybox 变体**上被咬过之后加的。
> 重写时**不要在没有对应证据的情况下简化它们** —— 那些证据就在代码注释里。

## 7. 差分测试发现的 shell 线缺陷（2026-09-22，重写过程中挖出）

这些是「只取逻辑、重写全部」过程的直接收获：**Rust 重写按契约实现后，与 shell 版的行为差
暴露了 shell 版自身的 bug**。逐条记录，供 shell 线修复（或作为 Rust 版"修掉而非照搬"的依据）。

### 7.1 空 apps 数组 + uid pin ⇒ 产出**非法 JSON**（丢收口 `]`）

- **触发**：`config.json` 的 apps 数组为空（`"apps":[]`）且 packages.list 里有 PI 核心三件套时，
  `apps-sync.sh` 的 uid-pin 插入走「空数组」分支：
  `s/"apps"\s*:\s*\[\]/"apps": [\n$INS\n/`
- **缺陷**：替换串以 `\n` 结尾，**没有把原来的收口 `]` 写回** ⇒ 产出
  `"apps": [\n"com.google.android.gms","uid:10101",…\n}}}` —— **没有 `]`，非法 JSON**。
  ConfigStore 下次读取会失败（按 v2.2.1 的先例：config 被污染 → TEE 隐藏失效）。
- **对照**：非空数组分支（`$INS,\n` + 既有条目）是对的。
- **复现**：`scripts/test-diff-apps-sync.sh` 的 `seed_gms` case（差分输出里标记为 KNOWN-SHELL-BUG）。
- **Rust 版**：`prepend_apps` 对空数组只插入条目、保留原 `]`，产出合法 JSON ✅。

### 7.2 迁移插入的重复键风险（shell 版措辞 vs Rust 版）

shell 的迁移 sed 把 `"apps":` **替换**为 `"autoIncludeNewApps": true, "apps":`（顺带规整了冒号空格）；
Rust 版首版错写成了「在 `"apps"` 前插入前缀 + 原文再带一次 `"apps"`」⇒ **重复键 + 非法 JSON**。
已修正为「替换而非追加」。**教训：插入型编辑必须明确"替换的是哪一段"。**
